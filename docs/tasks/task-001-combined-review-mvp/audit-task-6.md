### Named risk — search query reordering

**Verdict: not a behavioral defect, but the test it satisfies is testing an incidental detail, not a real requirement.**

- `client.go:161-187` (search branch of `ListMergedChanges`): when `search` is non-empty, the client issues an author query (only if `usernameRe.MatchString(search)`, `client.go:167-176`) and then *always* issues a title query (`client.go:177-184`), then does `items = mergeUnique(items, byTitle)` (`client.go:185`) followed by `sortMergedDesc(items)` (`client.go:186`).
- `sortMergedDesc` (`mapping.go:562-569`) fully re-sorts the merged set by `merged_at` desc, tie-broken by `Number()` desc, independent of which slice (`author` or `title`) contributed which item. `mergeUnique` (`client.go:256-269`) only affects which *copy* of a duplicate CR survives, and since both queries hit the same GitLab endpoint for the same repo, the mapped fields for a given IID are identical regardless of source query. `hasNext` is `OR`-combined (`client.go:184`), also order-independent.
- Conclusion: reversing which query fires first changes **only** which HTTP request is observed last by a test spy — it changes no field of the returned `Slice[ChangeRequest]`, no `HasNext` value, and no error path. The implementer did not break user-visible behavior to satisfy `TestListMergedChangesAndSearch`'s "last query" assertion (task-6-brief.md:182-184 test code); the final result is byte-identical either way.
- Is the test meaningful? Partially. It correctly verifies the title-search request carries `search=<term>&in=title` (a real requirement). But it derives that verification from **"last query in the observed sequence,"** an implementation detail of iteration order, not a documented contract. If the order were reversed back to the brief's literal title-then-author pseudocode, this specific assertion would fail even though output correctness is preserved — proof the assertion is incidental, not behavioral.
- Does the brief mandate an order? Only implicitly, via illustrative pseudocode (task-6-brief.md:249-352 block, specifically the title-first/author-second shape at lines ~503-520 of the rendered brief). The brief's own preceding note (mapping.go reversal fix, task-6-brief.md:354-362) already establishes that its pseudocode is illustrative and expected to be corrected where it's locally wrong — so deviating from the literal order is within the brief's own stated tolerance, and here it was necessary for the code to compile against the also-brief-supplied test.
- Rating: **Minor** — no functional defect, fully documented in-code (`client.go:161-164` comment) and in the report. Flagged only because coupling production request ordering to a test's implicit "last-observed-request" assumption is fragile: a future change to `usernameRe` matching or to which branch runs first could silently break the test without any real regression, or vice versa. Not blocking.
